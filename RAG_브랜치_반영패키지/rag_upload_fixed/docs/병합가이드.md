# 병합 가이드

이 패키지를 저장소에 반영하는 절차입니다.

모든 파일이 완성본으로 들어 있습니다. **손으로 옮길 코드는 없습니다.**
`pipeline/patrol_pipeline_rag.py` 도 포함되어 있으며, 저장소 파일과 대조해
잃을 기능이 없음을 확인한 뒤 넣었습니다(4절).

예외는 두 가지입니다. `set_env.example.sh` 는 기존 DB 설정을 지우지
않도록 블록만 덧붙이고(3절), 지식베이스 DB 를 나눠 쓰는 경우에만
`setup_knowledge_base.py` · `embed_chunks.py` 를 한 줄씩 고칩니다(5절).

## 4. `pipeline/patrol_pipeline_rag.py`

완성본이 패키지에 들어 있습니다. **그대로 복사하면 됩니다.**

전달받은 저장소 파일과 대조한 결과, 이 파일에는 TTS 송신·대응안 스로틀·
억제 간격이 들어 있지 않았습니다. 잃을 것이 없으므로 손으로 옮길 필요가
없습니다.

```bash
# 먼저 무엇이 바뀌는지 확인
diff -u <저장소>/rag_upload/pipeline/patrol_pipeline_rag.py \
        pipeline/patrol_pipeline_rag.py

cp pipeline/patrol_pipeline_rag.py <저장소>/rag_upload/pipeline/
```

diff 에 아래 다섯 가지 외의 변경이 보이면 그 저장소 파일이 이 패키지를
만든 시점 이후에 바뀐 것입니다. 그 경우 복사하지 말고 아래 "파일이
바뀌었다면" 으로 가십시오.

| 변경 | 내용 |
|---|---|
| UDP 기본값 | `127.0.0.1:9999` → `PIPELINE_UDP_BIND` / `DASHBOARD_UDP_PORT` (기본 `0.0.0.0:9998`) |
| `--use-llm` | 인자 추가, 에이전트 전달, 시작 로그에 실제 호출 대상 표시 |
| `--async-llm` | 인자 추가, 워커 배선, `--plan-queue-size` |
| `handle_plan()` | 대응안 후처리를 한곳으로 모음. TTS 를 붙일 자리 |
| 종료 처리 | 처리 결과 로그를 `finally` 맨 끝으로 이동 (비동기 건수 확정 후) |

기본값은 전부 꺼져 있습니다. `--async-llm` 을 켜지 않으면 지금까지의
동작 그대로입니다.

### TTS 를 나중에 붙일 때

`handle_plan()` 안에 넣으십시오. 동기·비동기 두 경로가 모두 이 함수를
거치므로 한 곳만 고치면 됩니다.

```python
    def handle_plan(plan) -> bool:
        ok = plan_writer.write_response_plan(plan)
        if ok and args.tts:
            tts_sender.send(plan)      # 여기
        return ok
```

수신 루프 안에서 직접 호출하면 `--async-llm` 을 켰을 때 음성이 나가지
않습니다. 비동기에서는 대응안이 워커 스레드에서 만들어지기 때문입니다.

### 파일이 바뀌었다면

저장소 파일이 그동안 바뀌어 복사할 수 없는 경우, `docs/apply_merge.py` 가
**추가만 하는** 방식으로 반영합니다. 기존 코드를 지우거나 옮기지 않으므로
나중에 들어간 기능이 사라지지 않습니다.

```bash
python3 docs/apply_merge.py --repo <저장소>/rag_upload --dry-run
python3 docs/apply_merge.py --repo <저장소>/rag_upload
```

UDP 기본값과 인자 추가까지 처리하며, 비동기 워커 배선은 하지 않고 안내만
합니다. 그 부분은 이 패키지의 완성본을 참고해 옮기십시오.

## 5. 지식베이스 스크립트 2개 (DB 를 나눠 쓸 때만)

단일 DB 구성이면 건너뛰십시오. 지식베이스를 운영 DB 와 다른 서버에 두는
경우에만 필요합니다.

`rag/setup_knowledge_base.py` 와 `rag/embed_chunks.py` 는 저장소에 이미
있는 파일이라 패키지에 넣지 않았습니다. 두 파일 모두 지식베이스 테이블을
직접 만지므로, 접속 대상을 지식베이스 쪽으로 돌려야 합니다.

각 파일에서 아래를

```python
from common.schema import get_db_config
...
cfg = get_db_config()
```

이렇게 바꿉니다.

```python
from rag.kb_config import get_kb_db_config
...
cfg = get_kb_db_config()
```

`get_kb_db_config()` 는 `RAG_KB_*` 환경변수가 없으면 운영 DB 설정을 그대로
돌려주므로, 단일 DB 구성에서도 동작이 달라지지 않습니다. 두 파일이
`get_db_config` 를 다른 이름으로 쓰고 있다면 호출 지점만 맞추면 됩니다.

`common.schema` 의 다른 import(예: `DetectionEvent`)는 그대로 두십시오.
바꾸는 것은 접속 설정 한 곳뿐입니다.

확인은 이렇게 합니다.

```bash
source set_env.sh
python3 rag/kb_config.py          # 대상 DB 와 구성 출력
python3 rag/check_pgvector.py     # 같은 DB 를 보고 있는지 확인
```

## 6. 줄바꿈 정리

이 패키지의 파일은 모두 LF 입니다. 복사 후 CRLF 가 섞이지 않았는지
확인하십시오.

```bash
git diff --check
file pipeline/patrol_pipeline_rag.py integration/response_agent.py
```

`with CRLF line terminators` 가 보이면 변환합니다.

```bash
sed -i 's/\r$//' pipeline/patrol_pipeline_rag.py
```

## 8. 브랜치에 올리지 않을 것

| 항목 | 이유 |
|---|---|
| `set_env.sh` | DB 비밀번호가 들어 있습니다 |
| 외부 전달용 ZIP 파일 | 소스 파일로 커밋해야 이력이 남습니다 |
| Ollama 설치 파일 · `gemma2:2b` 모델 | 각 PC 에서 내려받습니다 |
| BGE-M3 모델 캐시 | 임베딩 실행 PC 에서 내려받습니다 |
| `__pycache__/`, `*.pyc` | `.gitignore` 확인 |

```bash
git status --short
git add -A
git status --short          # set_env.sh 가 목록에 없는지 확인
```
