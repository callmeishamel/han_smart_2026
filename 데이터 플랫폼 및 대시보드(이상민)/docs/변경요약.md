# 이번 브랜치 변경 내용

RAG 대응안 생성 파트의 반영 내용입니다.

이 대시보드 폴더에는 패키지 작성 이후 추가된 TTS 송신, 대응안 스로틀,
자동 구역 판정, 공통 SQL 기능이 이미 있었습니다. 따라서 패키지의 파이프라인
완성본으로 덮어쓰지 않고 비동기 LLM 워커와 환경설정만 병합했으며, 기존
기능은 모두 유지했습니다. `docs/병합가이드.md`는 외부 패키지의 원본 반영
절차를 기록한 참고 문서이고, 현재 폴더에는 이미 반영이 끝난 상태입니다.

---

## 수정 3개

### `integration/response_agent.py`

**지식베이스 확인 실패가 영구 캐싱되던 문제를 고쳤습니다.**

DB 연결이 한 번 실패하면 `_kb_ready = False` 가 굳어서, DB 가 복구돼도 계속
내장 지침(확신도 0.4)으로만 동작했습니다. 성공한 결과는 그대로 재사용하고,
실패한 결과만 60초 뒤 재확인하도록 바꿨습니다. 매번 재시도하면 DB 가 죽어
있을 때 30fps 로 연결을 두드리게 되므로 간격을 뒀습니다.

**`use_llm` 인자를 추가했습니다.**

`rag/vllm_client.py` 는 저장소에 있었으나 호출 경로가 없어 실행되지 않는
상태였습니다. 서버가 없거나 응답하지 않으면 규칙 기반 문장으로 자동
대체되므로, 켜 두어도 기존 동작에 영향이 없습니다.

**LLM 생성 문장에도 500자 제한을 적용합니다.**

`response_plans.recommended_action` 은 `VARCHAR(500)` 인데, 규칙 기반
문장만 자르고 LLM 문장은 그대로 저장하고 있었습니다. 생성이 길게 나오면
INSERT 가 실패해 대응안이 통째로 유실됩니다. 모의 LLM 으로 600자를
반환시켜 재현했습니다.

두 경로가 같은 `_truncate()` 를 거치도록 바꿨습니다. 줄바꿈과 연속 공백도
함께 정리합니다. LLM 출력은 줄바꿈이 섞여 나오는데 대시보드는 한 줄로
표시하기 때문입니다.

**LLM 응답 키가 없어도 죽지 않게 했습니다.**

`result['latency_ms']` 와 `result['text']` 를 직접 참조하고 있어, 클라이언트가
그 키를 넣지 않으면 `KeyError` 로 대응안 생성 전체가 끝났습니다. `.get()` 으로
바꾸고, dict 가 아닌 응답과 호출 예외까지 규칙 기반으로 넘어가도록
막았습니다. 이 클래스는 어떤 상황에서도 ResponsePlan 을 돌려주기로 되어
있는데 그 계약이 깨져 있던 부분입니다.

**`LLM_TIMEOUT` 을 클라이언트에 전달합니다.**

설치 가이드가 CPU 추론 환경에 `LLM_TIMEOUT=180` 을 안내하는데, 클라이언트가
이 값을 읽지 않아 안내대로 설정해도 기본 타임아웃에서 끊겼습니다.
`LLM_BASE_URL` · `LLM_MODEL` 과 같은 방식으로 넘깁니다. 구버전 `LlmClient`
가 `timeout` 인자를 받지 않는 경우는 `TypeError` 로 걸러 내고 기존 방식으로
다시 생성하므로, 클라이언트를 아직 고치지 않아도 동작합니다.

### `rag/check_pgvector.py` · `rag/check_llm.py`

**존재하지 않는 문서를 안내하던 부분을 고쳤습니다.**

| 안내하던 경로 | 실제 |
|---|---|
| `docs/pgvector_설치안내.md` | `docs/설치가이드_리눅스.md` 1절 |
| `docs/LLM서버_구동안내.md` | `docs/설치가이드_리눅스.md` 3절 |

두 파일 모두 저장소에 없습니다. 안내대로 찾다가 막히는 것을 막기 위해
설치가이드의 해당 절을 가리키도록 바꿨습니다.

`check_pgvector.py` 에는 파이썬 `pgvector` 패키지와 PostgreSQL 서버 확장이
다르다는 안내를 추가했습니다. 패키지만 설치하고 벡터 검색이 안 켜진다는
문의가 나오기 쉬운 지점입니다.

`check_llm.py` 는 `LLM_TIMEOUT` 을 반영하고 시작 출력에 표시합니다.

### `pipeline/patrol_pipeline_rag.py`

완성본으로 들어 있습니다. 바뀐 것은 다섯입니다.

1. **UDP 기본값을 환경변수로.** 기존 `127.0.0.1:9999` 는 ROS2 브릿지 포트와
   겹칩니다. `PIPELINE_UDP_BIND`(기본 `0.0.0.0`) · `DASHBOARD_UDP_PORT`(기본
   `9998`)를 읽도록 바꿨습니다.
2. **`--use-llm` 추가** — 에이전트 전달, 시작 로그에 실제 호출 대상 표시.
3. **`--async-llm` · `--plan-queue-size` 추가** — 아래 참조.
4. **`handle_plan()` 신설** — 대응안 후처리를 한곳으로 모았습니다. 동기와
   비동기가 같은 함수를 거치므로, 나중에 TTS 를 붙일 때 이 안에만 넣으면
   두 경로 모두에 적용됩니다. 수신 루프에서 직접 호출하면 `--async-llm` 을
   켰을 때 음성이 빠집니다.
5. **종료 처리** — 처리 결과 로그를 `finally` 맨 끝으로 옮겼습니다.
   비동기에서는 워커를 정리해야 대응안 건수가 확정되기 때문입니다.
   docstring 의 포트 표기도 갱신했습니다.

## 비동기 대응안 생성 (`--async-llm`)

**해결하는 문제.** `--use-llm` 을 켜면 `generate_response()` 안에서 GEMMA 2B
응답을 기다립니다. CPU 추론(Ollama)에서는 한 건에 수 초에서 수십 초가
걸리고, 그동안 UDP 수신 루프가 그대로 멈춥니다. UDP 는 재전송이 없으므로
그 사이 도착한 탐지 패킷은 소켓 버퍼가 차는 순간 커널에서 버려지고,
`patrol_logs` 에도 남지 않습니다. 대응안 한 건을 만드느라 탐지 기록을 잃는
구조입니다.

**구성.** 생성 단계만 큐와 워커 스레드로 옮깁니다. 수신 루프는 큐에 넣고
즉시 돌아갑니다.

```
(기존)  UDP 수신 -> 적재 -> 대응안 생성 대기 -> 적재 -> 다음 수신
(워커)  UDP 수신 -> 적재 -> 큐 투입 -> 다음 수신
                              L 워커 스레드에서 생성 -> 적재
```

**기본값은 꺼 둡니다.** 지금까지의 동작이 그대로 유지되고, 필요할 때만
`--async-llm` 으로 켭니다.

```bash
./run_pipeline_rag.sh --use-llm                            동기 (기존 동작)
./run_pipeline_rag.sh --use-llm --async-llm                비동기
./run_pipeline_rag.sh --use-llm --async-llm --plan-queue-size 64
```

**설계상 지켜야 하는 것 세 가지.** 워커 파일 상단에도 같은 내용을 적어
뒀습니다.

1. `RagResponseAgent` 인스턴스는 워커 전용입니다. 내부에 psycopg2 커넥션과
   임베딩 모델을 잠금 없이 들고 있어, 메인 루프에서 같은 인스턴스를 함께
   쓰면 커넥션이 깨집니다.
2. 대응안 적재용 DB 커넥션은 메인 루프와 분리합니다. psycopg2 커넥션을 두
   스레드가 공유하면 한쪽 `commit` 이 다른 쪽의 열린 트랜잭션까지
   커밋합니다. 병합가이드의 코드는 워커용 `RagPatrolLogWriter` 를 따로
   만듭니다.
3. 중복 억제(`ResponsePlanThrottle`)는 `submit()` 앞에서 판정합니다. 큐에
   넣은 뒤에 걸러 봐야 이미 자리를 차지한 뒤입니다.

**큐가 밀릴 때.** 기본 32건이 차면 가장 오래 기다린 건을 버리고 새 이벤트를
넣습니다. 안전 관제에서는 3분 전 상황의 대응안보다 방금 감지된 상황의
대응안이 쓸모 있기 때문입니다. 버려지는 것은 대응안뿐이고, 탐지 이벤트
자체는 메인 루프에서 이미 `patrol_logs` 에 적재된 뒤입니다. 순서를 그대로
남겨야 하면 `drop_policy="newest"` 로 바꿀 수 있습니다.

포화 경고는 10초에 한 번만 출력합니다. 매 이벤트마다 찍으면 다른 로그가
덮입니다.

**종료.** `close()` 는 남은 건을 최대 15초까지 처리하고 정리합니다. 생성이
느린 환경에서 큐가 남아 있으면 종료가 무한정 늘어지므로 기한을 뒀습니다.
기한을 넘긴 건은 `discarded` 로 집계해 종료 로그에 찍힙니다.

**남은 한계.** 워커는 한 스레드입니다. 위험 등급 이벤트가 LLM 생성 속도보다
꾸준히 빠르게 들어오면 큐는 결국 밀립니다. 이 구성이 지키는 것은 "수신
루프가 멈추지 않는다"이지 "모든 위험 이벤트에 대응안이 생성된다"가
아닙니다. 실사용에서 `dropped` 가 계속 쌓이면 LLM 서버를 GPU 로 옮기거나,
위험 등급 판정 기준을 좁히거나, 워커 수를 늘려야 합니다. 워커 수를 늘릴
때는 에이전트와 DB 커넥션도 스레드마다 따로 만들어야 합니다.

## 지식베이스 DB 분리 (`rag/kb_config.py`)

**해결하는 문제.** 팀 공용 DB 가 윈도우에 있고 파이프라인은 리눅스에서
도는 구성에서, pgvector 를 어디에 설치할지가 막힙니다. 확장은 서버 측
기능이라 postgres 가 도는 PC 에 설치해야 하는데, 윈도우는 리눅스의
`make` · `pgxs.mk` 경로가 통째로 맞지 않아 사전 빌드 바이너리를 찾거나
Visual Studio Build Tools 로 `nmake` 빌드를 해야 합니다.

**구성.** 지식베이스만 리눅스 쪽 로컬 DB 에 두고, 운영 테이블은 팀 공용
DB 에 그대로 둡니다.

```
팀 공용 DB (윈도우)     patrol_logs, response_plans, event_logs
                        대시보드가 읽습니다. 파이프라인이 씁니다.

지식베이스 DB (리눅스)   safety_documents, safety_chunks,
                        response_guidelines
                        대응안 생성이 읽기만 합니다. pgvector 는 여기만.
```

**나눠도 안전한 이유.** `response_plans.reference_docs` 는 청크 외래키가
아니라 문서 제목 TEXT 입니다. 대시보드는 근거 목록을 팀 공용 DB 에서
그대로 받으며, 두 DB 를 조인할 일이 없습니다. 지식베이스는 대응안 생성이
읽기만 하므로 쓰기 경로가 갈라지지도 않습니다.

**기본값은 단일 DB 입니다.** `RAG_KB_HOST` 나 `RAG_KB_NAME` 을 설정했을
때만 갈라집니다. 설정하지 않으면 `get_kb_db_config()` 가 운영 DB 설정을
그대로 돌려주므로, 이 파일을 넣어도 기존 구성은 달라지는 것이 없습니다.
개별 항목을 생략하면 같은 이름의 `SFP_DB_*` 값을 씁니다.

```bash
python3 rag/kb_config.py
```

```
지식베이스 localhost:5432/smart_factory_kb / 운영 DB 203.0.113.30:5432/smart_factory_db
분리 구성
```

**함께 손봐야 하는 파일.** `rag/setup_knowledge_base.py` 와
`rag/embed_chunks.py` 도 지식베이스를 직접 만지므로 접속 대상을 맞춰야
합니다. 저장소에 이미 있는 파일이라 패키지에 넣지 않았고, 한 줄짜리
변경을 병합가이드 5절에 실었습니다. 단일 DB 구성이면 손댈 필요가
없습니다.

## 설정 파일

`set_env.example.sh` 에 덧붙일 블록을 `docs/set_env_llm_block.sh` 로
분리했습니다. 기존 `SFP_DB_*` 설정을 덮어쓰지 않도록 파일을 교체하지 말고
블록만 추가하십시오.

```bash
cat docs/set_env_llm_block.sh >> set_env.example.sh
```

추가되는 항목입니다.

| 변수 | 기본 | 용도 |
|---|---|---|
| `PIPELINE_UDP_BIND` | `0.0.0.0` | UDP 수신 바인드 주소 |
| `DASHBOARD_UDP_PORT` | `9998` | 비전 모듈이 보내는 포트 |
| `LLM_BASE_URL` | Ollama `:11434/v1` | LLM 서버 주소 |
| `LLM_MODEL` | `gemma2:2b` | 모델명 |
| `LLM_TIMEOUT` | `180` | 생성 타임아웃(초), CPU 추론 기준 |
| `RAG_KB_HOST` 외 4개 | 미설정 | 지식베이스 DB 분리. 설정할 때만 갈라집니다 |

## 손대지 않은 것

**`common/schema.py`** — `DISTANCE_BASED_OBJECTS` 가 `{"human", "vehicle"}`
인데 비전 모듈 탐지 클래스에는 `person` 도 있습니다. 거리 기반 판정
대상에서 빠집니다. 데이터 플랫폼 파트 파일이라 손대지 않았습니다.

**TTS 방송 문장** — 기존 `--tts` 송신 기능을 유지하고, 동기·비동기
대응안이 모두 `handle_plan()`을 거치도록 병합했습니다. 현재는 화면용
대응안 전문을 보내므로, 운영 단계에서는 재생 시간이 짧은 방송 문장을
별도로 구성하는 개선이 필요합니다.

**위험 등급 판정 기준** — 대응안은 `risk_level == "위험"` 에서만
생성합니다. 주의 등급까지 넓히면 같은 내용이 반복 저장되고 연산 부담도
커집니다.
