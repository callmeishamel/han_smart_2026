# 설치 가이드 (Linux)

pgvector, GEMMA 2B, 임베딩을 설치하는 절차입니다.

**셋 다 설치하지 않아도 대응안은 생성됩니다.** 검색 정확도와 문장 품질을
올리는 단계입니다.

---

## 빠른 시작

**처음 설치하는 것이라면 이 문서 대신 `시작하기.md` 를 보십시오.**
한 장이고, 아래 절차를 스크립트가 대신합니다. 이 문서는 스크립트가 막혔을
때 무엇을 어떻게 하는지 찾아보는 참조용입니다.

```bash
cd '<저장소>/데이터 플랫폼 및 대시보드(이상민)'
cp set_env.example.sh set_env.sh && nano set_env.sh   # DB 접속 정보 입력
source set_env.sh

./setup_linux.sh --check     # 무엇이 빠졌는지 확인
./setup_linux.sh             # 빠진 것만 설치

python3 rag/setup_knowledge_base.py    # 지식베이스 적재 (한 번만)
```

여기까지가 필수입니다. 실행은 이렇게 합니다.

```bash
./run_pipeline_rag.sh
```

아래는 전부 선택입니다. 하나도 안 해도 대응안은 생성됩니다.

| 원하는 것 | 절 | 설치할 것 |
|---|---|---|
| 문장 품질 (GEMMA 2B) | 3 | Ollama + `ollama pull gemma2:2b` |
| 검색 정확도 (벡터) | 1~2 | pgvector 확장 + BGE-M3 |
| 수신 누락 방지 | 4-1 | 없음. `--async-llm` 플래그만 |

DB 가 두 대이거나 어느 PC 에 무엇을 까는지 헷갈리면 문서 뒤쪽
"어느 PC에 무엇을 설치하는가" 를 먼저 보십시오.

## 0. 사전 준비

```bash
cd '<저장소>/데이터 플랫폼 및 대시보드(이상민)'
cp set_env.example.sh set_env.sh
nano set_env.sh          # SFP_DB_PASSWORD, SFP_DB_HOST 입력

pip3 install -r rag/requirements.txt
source set_env.sh
```

`set_env.example.sh` 에 LLM · UDP 항목이 없으면 먼저 덧붙이십시오.
파일을 교체하면 기존 DB 설정이 지워집니다.

```bash
cat docs/set_env_llm_block.sh >> set_env.example.sh
```

### UDP 포트

RAG 파이프라인은 **9998** 을 받습니다.

```
9999   비전 모듈 -> ROS2 브릿지
9998   비전 모듈 -> 대시보드 · DB / RAG 파이프라인
9091   미니맵
```

9999 로 맞추면 ROS2 브릿지와 같은 포트를 두고 다투게 되어 한쪽만 패킷을
받습니다. 값은 환경변수로 바꿉니다.

```bash
export PIPELINE_UDP_BIND=0.0.0.0
export DASHBOARD_UDP_PORT=9998
```

### 지식베이스 구성 (필수)

```bash
python3 rag/setup_knowledge_base.py
```

산업안전 지침 19건이 들어갑니다. 두 번 실행해도 중복되지 않습니다.

```
테이블 생성 완료: safety_documents, safety_chunks
적재 완료: 문서 3건, 청크 19건
```

`pgvector 확장: 미설치` 는 오류가 아닙니다. 벡터 검색 없이 위험유형
기준으로 근거를 찾는 방식으로 동작합니다.

**여기까지만 해도 파이프라인이 돕니다.**

## 1. pgvector (벡터 검색)

**지식베이스 DB 가 있는 PC 에서 실행합니다.** DB 를 두 대로 나눈 구성이면
리눅스 쪽 로컬 DB 가 대상이고, 운영 DB 에는 설치하지 않아도 됩니다.

### 1-1. 개발 헤더 설치

이걸 빠뜨리면 `make` 에서 `pgxs.mk` 오류가 납니다.

```bash
# RHEL / Rocky
sudo dnf install -y postgresql18-devel

# Ubuntu / Debian
sudo apt install -y postgresql-server-dev-18 build-essential
```

버전 숫자는 `psql --version` 결과에 맞춥니다.

`Unable to read consumer identity` 가 나오면 PGDG 저장소를 먼저
등록합니다.

```bash
sudo dnf install -y https://download.postgresql.org/pub/repos/yum/reporpms/EL-8-x86_64/pgdg-redhat-repo-latest.noarch.rpm
```

### 1-2. 빌드 및 설치

```bash
cd /tmp
git clone https://github.com/pgvector/pgvector.git
cd pgvector

export PG_CONFIG=/usr/pgsql-18/bin/pg_config
make
sudo PG_CONFIG=/usr/pgsql-18/bin/pg_config make install
```

`sudo` 는 환경변수를 지우므로 `PG_CONFIG` 를 다시 넘겨야 합니다.

### 1-3. 확장 활성화

```bash
psql -U postgres -d smart_factory_db -c "CREATE EXTENSION IF NOT EXISTS vector;"
psql -U postgres -d smart_factory_db -c "\dx"
```

`vector | 0.8.2` 가 보이면 성공입니다.

확장은 DB 단위입니다. `postgres` DB 에서 만들면 `smart_factory_db` 에는
적용되지 않습니다.

### 1-4. 컬럼 준비

```bash
cd '<저장소>/데이터 플랫폼 및 대시보드(이상민)'
python3 rag/check_pgvector.py
```

`embedding` 컬럼과 인덱스를 자동으로 추가합니다. 지식베이스를 다시 만들
필요는 없습니다.

## 3. GEMMA 2B (문장 생성)

### 3-1. 실행기 선택

**기본은 Ollama 입니다.** Ollama 는 CPU 에서도 GPU 에서도 돌아가며,
NVIDIA GPU 가 있으면 알아서 씁니다. 설치가 한 줄이라 대부분 이쪽이면
충분합니다.

**vLLM 은 NVIDIA GPU 가 있고 처리량이 필요할 때만** 고려하십시오.
CUDA 환경에서만 설치되고, GEMMA 라이선스 동의와 모델 내려받기가 따로
필요합니다. 순찰 로봇은 위험 이벤트에서만 생성을 호출하므로 초당 처리량이
문제 되는 구간이 아닙니다.

가진 GPU 는 이렇게 확인합니다. 결과는 참고용이고, 없어도 Ollama 는
그대로 씁니다.

```bash
nvidia-smi
```

모델은 둘 다 GEMMA 2B 로 같고, 환경변수 두 개만 다릅니다.
아래 3-2a 와 3-2b 중 하나만 하면 됩니다.

### 3-2a. vLLM (NVIDIA GPU + 처리량이 필요할 때)

```bash
pip3 install vllm
huggingface-cli login          # GEMMA 라이선스 동의 필요

python3 -m vllm.entrypoints.openai.api_server \
    --model google/gemma-2-2b-it \
    --host 0.0.0.0 --port 8000 \
    --max-model-len 4096 --gpu-memory-utilization 0.85
```

`set_env.sh` 에 추가합니다.

```bash
export LLM_BASE_URL=http://localhost:8000/v1
export LLM_MODEL=google/gemma-2-2b-it
export LLM_TIMEOUT=60
```

### 3-2b. Ollama (기본 권장 · CPU/GPU 모두)

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull gemma2:2b
```

설치 스크립트가 systemd 서비스까지 등록하므로 별도 실행이 필요 없습니다.

```bash
sudo systemctl status ollama
```

`set_env.sh` 에 추가합니다.

```bash
export LLM_BASE_URL=http://localhost:11434/v1
export LLM_MODEL=gemma2:2b
export LLM_TIMEOUT=180
```

CPU 추론은 첫 요청이 특히 느립니다. 기본값 60초로는 끊기는 경우가 있어
180초를 권장합니다.

LLM 서버가 파이프라인과 다른 PC 에 있다면 `localhost` 대신 그 PC 의 주소를
넣고, 서버를 `--host 0.0.0.0` 으로 띄워야 합니다.

### 3-3. 확인

```bash
source set_env.sh
python3 rag/check_llm.py
```

Fast Path 와 Slow Path 지연을 비교 측정합니다.

## 4. 실행

```bash
./run_pipeline_rag.sh                              기본
./run_pipeline_rag.sh --use-embedding              벡터 검색
./run_pipeline_rag.sh --use-embedding --use-llm    전체
```

정상 로그입니다.

```
[INFO] 적재 완료 [A] 화재 (위험도: 위험, 거리: 3.5m)
[INFO] 대응 지침 생성 [A] 확신도 0.60 | 근거 3건
```

`적재 완료` 만 뜨는 건 정상입니다. 위험 등급이 아닌 경우입니다.

### 4-1. CPU 추론이면 `--async-llm` 을 함께 켜십시오

`--use-llm` 만 켜면 GEMMA 2B 응답이 끝날 때까지 UDP 수신 루프가 멈춥니다.
UDP 는 재전송이 없으므로, 그 사이 도착한 탐지 패킷은 소켓 버퍼가 차는 순간
버려지고 `patrol_logs` 에도 남지 않습니다. GPU 가 없는 환경에서는 생성 한
건에 수 초에서 수십 초가 걸려 실제로 누락이 발생합니다.

`--async-llm` 은 생성 단계를 별도 스레드로 분리합니다. 수신 루프는 큐에
넣고 즉시 돌아가므로 적재가 계속됩니다.

```bash
./run_pipeline_rag.sh --use-llm --async-llm
./run_pipeline_rag.sh --use-llm --async-llm --plan-queue-size 64
```

종료할 때 처리 결과가 찍힙니다.

```
[INFO] 비동기 대응안: 생성 12건 / 적재 12건 / 드롭 0건 / 실패 0건 / 최대대기 8420ms
```

`드롭` 이 계속 늘어나면 LLM 생성이 이벤트 속도를 따라가지 못하는 상태입니다.
탐지 적재는 계속되지만 대응안이 빠집니다. LLM 서버를 GPU 로 옮기거나 위험
등급 판정 기준을 좁혀야 합니다.

`최대대기` 는 큐에 들어가서 생성이 시작되기까지의 최대 지연입니다. 이 값이
분 단위로 올라가면 대응안이 이미 지난 상황을 가리키고 있다는 뜻입니다.

기본값은 꺼져 있습니다. 켜지 않으면 지금까지의 동작 그대로입니다.

## 어느 PC에 무엇을 설치하는가

같은 이름이 여러 곳에 나와 혼동하기 쉬운 부분입니다. 먼저 확인하십시오.

| 항목 | 설치 위치 | 저장소에 포함 |
|---|---|---|
| 수정 Python 파일 · 문서 | 저장소를 실행하는 PC | 포함 |
| PostgreSQL `vector` 확장 | **DB 서버가 떠 있는 PC** | 미포함 |
| Python `pgvector` 패키지 | RAG 파이프라인 실행 PC | requirements 만 |
| Ollama (또는 vLLM) | LLM 서버 PC | 미포함 |
| `gemma2:2b` 모델 | `ollama pull` 을 실행한 PC | 미포함 |
| BGE-M3 모델 캐시 | 임베딩을 실행하는 PC | 미포함 |
| `set_env.sh` (DB 비밀번호) | 각 PC 에서 직접 작성 | **절대 미포함** |

특히 **PostgreSQL 확장과 Python 패키지는 다릅니다.** 파이프라인 PC 에서
`pip install pgvector` 만 해서는 DB 의 벡터 기능이 켜지지 않습니다. 서버 측
확장은 DB 가 설치된 PC 에서 1절 절차를 따라 설치해야 합니다.

세 가지가 각각 다른 PC 에 있어도 됩니다. 주소만 환경변수로 맞추면 됩니다.

## DB 를 두 대로 나눠 쓰는 경우

팀 공용 DB 가 윈도우에 있고 파이프라인은 리눅스에서 도는 구성이라면,
지식베이스만 리눅스 쪽 로컬 DB 에 두는 편이 낫습니다.

```
팀 공용 DB (윈도우)     patrol_logs, response_plans, event_logs
                        대시보드가 읽습니다. 파이프라인이 씁니다.

지식베이스 DB (리눅스)   safety_documents, safety_chunks,
                        response_guidelines
                        대응안 생성이 읽기만 합니다. pgvector 는 여기만 필요합니다.
```

**왜 나누는가.** pgvector 는 서버 측 확장이라 postgres 가 도는 PC 에
설치해야 합니다. 윈도우는 리눅스의 `make` · `pgxs.mk` 경로가 통째로 맞지
않아, PostgreSQL 버전에 맞는 사전 빌드 바이너리를 찾거나 Visual Studio
Build Tools 로 `nmake` 빌드를 해야 합니다. 반면 지식베이스는 청크 수십
건짜리 읽기 전용이고 대시보드가 조회하지도 않으므로, 리눅스 쪽에 두면
1절 절차를 그대로 쓸 수 있습니다.

**나눠도 안전한 이유.** `response_plans.reference_docs` 는 청크 외래키가
아니라 문서 제목 TEXT 입니다. 대시보드는 근거 목록을 팀 공용 DB 에서
그대로 받으며, 두 DB 를 조인할 일이 없습니다.

**설정.** `set_env.sh` 에 아래를 추가하면 지식베이스만 그쪽을 봅니다.
설정하지 않으면 지금까지처럼 `SFP_DB_*` 하나로 동작하므로, 단일 DB
구성이라면 이 절을 건너뛰면 됩니다.

```bash
export RAG_KB_HOST=localhost
export RAG_KB_PORT=5432
export RAG_KB_NAME=smart_factory_kb
export RAG_KB_USER=postgres
export RAG_KB_PASSWORD=...
```

생략한 항목은 같은 이름의 `SFP_DB_*` 값을 씁니다. 같은 서버의 다른
데이터베이스만 쓰려면 `RAG_KB_NAME` 하나만 설정하면 됩니다.

확인은 이렇게 합니다.

```bash
source set_env.sh
python3 rag/kb_config.py
```

```
지식베이스 localhost:5432/smart_factory_kb / 운영 DB 203.0.113.30:5432/smart_factory_db
분리 구성
```

**이 구성에서는 아래 절의 DB 작업이 전부 지식베이스 쪽입니다.**
`setup_knowledge_base.py`, `check_pgvector.py`, `embed_chunks.py` 는 모두
`RAG_KB_*` 를 따라갑니다. 운영 DB 에는 pgvector 를 설치하지 않아도 됩니다.

## 설치 상태별 동작

| 설치 | 경로 | 확신도 |
|---|---|---|
| pgvector + LLM | 벡터 검색 + GEMMA 생성 | 0.75~0.95 |
| pgvector만 | 벡터 검색 + 규칙 기반 | 0.70~0.95 |
| LLM만 | 위험유형 조회 + GEMMA 생성 | 0.65 |
| 없음 | 위험유형 조회 + 규칙 기반 | 0.60 |
| DB 연결 불가 | 내장 지침 | 0.40 |

`response_plans.confidence` 로 어느 경로였는지 확인합니다.

## 자주 막히는 지점

**`pgxs.mk: 그런 파일이나 디렉터리가 없습니다`**
→ 1-1 개발 헤더 설치를 건너뛴 경우입니다.

**`make install` 시 Permission denied**
→ `sudo PG_CONFIG=... make install` 로 환경변수를 함께 넘기십시오.

**`SFP_DB_PASSWORD가 비어 있습니다`**
→ `source set_env.sh` 를 먼저 실행하십시오.

**`common` 또는 `integration` 모듈을 찾을 수 없습니다**
→ `pipeline/` 폴더 안에서 직접 실행하지 말고 위 프로젝트 루트에서
`python3 pipeline/patrol_pipeline_rag.py ...` 형태로 실행하십시오.

**탐지 이벤트가 하나도 들어오지 않음**
→ 포트를 확인하십시오. RAG 파이프라인은 9998 입니다. 9999 는 ROS2
브릿지가 쓰고 있어, 같은 포트를 잡으면 한쪽만 받습니다.

```bash
python3 pipeline/patrol_pipeline_rag.py --help | grep udp-port
ss -lunp | grep 9998
```

**LLM 응답이 오지 않음**
→ CPU 추론이면 첫 요청이 느립니다. `export LLM_TIMEOUT=180` 후
`source set_env.sh` 를 다시 실행하십시오. 값이 실제로 적용됐는지는
`python3 rag/check_llm.py` 시작 출력의 `타임아웃` 줄로 확인합니다.

**LLM 을 켠 뒤 탐지 로그가 띄엄띄엄 찍힘**
→ 생성이 수신 루프를 막고 있습니다. `--async-llm` 을 함께 켜십시오(4-1절).

**DB 연결 실패**
→ 파이프라인은 멈추지 않습니다. 확신도 0.40 으로 동작하고, DB 가
복구되면 60초 안에 자동으로 다시 인식합니다.

**`pip install pgvector` 를 했는데 벡터 검색이 안 켜짐**
→ 파이썬 패키지와 PostgreSQL 서버 확장은 별개입니다. DB 가 설치된 PC 에서
1절 절차로 확장을 설치해야 합니다.

**확장을 깔았는데 `check_pgvector.py` 가 계속 없다고 함**
→ 보고 있는 DB 가 다를 수 있습니다. `python3 rag/kb_config.py` 로 대상을
확인하십시오. 확장은 DB 단위라, `postgres` DB 에서 만들면 지식베이스
DB 에는 적용되지 않습니다.

**지식베이스는 리눅스인데 대응안이 운영 DB 에 안 쌓임 (또는 그 반대)**
→ `RAG_KB_*` 는 지식베이스 조회에만 적용됩니다. `patrol_logs` 와
`response_plans` 는 언제나 `SFP_DB_*` 쪽에 씁니다. 둘이 뒤바뀌었으면
환경변수를 다시 확인하십시오.
