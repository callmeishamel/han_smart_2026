커밋됨 · 미배포

젯슨이 잡은 person이 미니맵에 작업자로 안 찍히던 문제

원인이 두 군데였습니다. 라벨 변환은 멀쩡했고 문제는 그 앞 단계였습니다.

① 젯슨에서 person이 아예 나가지 못했습니다

겹친 탐지를 text_prompt 순서로만 정리해서, "person with no helmet"(0번)과 "person"(1번)이 같은 사람에 걸리면 점수와 무관하게 항상 일반 person이 지워졌습니다. threshold=0.1은 낮고 두 프롬프트는 person 토큰을 공유하므로, 안전모를 쓴 작업자에게도 위반 쿼리가 함께 걸리는 것이 보통입니다.

이제 점수로 정하되 위반 클래스에 HELMET_SAFETY_MARGIN(0.05) 가산점을 줍니다.

② 사람은 SLAM 지도에 없습니다

저장된 occupancy grid에만 레이캐스팅해서, 열린 통로의 작업자는 None이 되어 통째로 버려지고 벽 앞의 작업자는 레이가 사람을 통과해 뒤쪽 벽에 찍혔습니다.

raycast_to_live_obstacle()이 /scan 기반 실시간 장애물(= 그 작업자)을 먼저 봅니다.

LiDAR 장애물 빨간 점 제거

occupancy grid에는 물체 종류 정보가 없어 벽과 적재물을 모양으로만 추정해야 했고, 빗나가면 벽 위에 점이 줄줄이 찍혔습니다. 레이어를 통째로 제거했습니다.

남긴 것

/scan 기반 실시간 장애물 계산은 그대로 뒀습니다 — 위 ②의 작업자 마커에 필요합니다.

자율 매핑이 갔던 곳을 왕복하던 문제

auto_mapper.py는 지나온 곳을 전혀 기억하지 않는 순수 랜덤워크였습니다.

미탐사 방향 선호(벽 뒤는 세지 않음) + 방문 기억(0.5m 격자 진입 횟수) + 회전 고정·재조정. 안전 로직은 그대로입니다.

스테레오 캘리브레이션 도입

거리는 Z = f × B / d인데 f=500.0 / B=0.06이 추측값이었고, 같은 f가 미니맵 방향각에도 쓰입니다. 게다가 cv2.StereoSGBM이 전제하는 정렬(rectification) 단계가 아예 없었습니다.

stereo_calibrate.py로 촬영 → 계산 → 검증하고, sender가 결과 파일이 있으면 자동으로 읽어 캡처 스레드에서 정렬합니다.

커밋 전

지도 기반 순찰 경로 자동 생성 + 대시보드에서 시작

patrol_node.py의 기본 웨이포인트는 시뮬레이션 좌표라 실물 지도에서는 지도 밖이거나 벽 속입니다. 그러면 Nav2가 모든 목표를 ABORTED로 돌려주는데, patrol_node는 재시도 후 다음 지점으로 넘어가므로 로그만 보면 순찰이 도는 것처럼 보입니다.

새 patrol_planner.py가 지금 지도에서 직접 경로를 만듭니다.

  1. 여유 공간 — 벽까지 거리를 재서 기준 미만 제외. 미탐사도 장애물로 침
  2. 도달 가능성 — 로봇이 있는 연결 성분만. 문 닫힌 옆방 제외
  3. 구역 — 미니맵이 이미 나눈 것을 그대로 사용
  4. 지점 선정 — 벽에서 멀되 구석이 아닌 자리
  5. 순서 — 측지거리 + 최근접이웃 + 2-opt

직선거리로 순서를 정하면 벽을 뚫고 가는 순서가 나옵니다. 빗 모양 통로에서 옆 통로는 직선 4.0m지만 실제로는 11.4m를 돌아가야 합니다 (자체 테스트 기준 실제 이동거리 측지 37.2m / 직선 40.0m).

자동 시작을 안 한 이유

페이지가 열릴 때 자동으로 시작하지 않습니다. Streamlit은 버튼 하나만 눌러도 스크립트를 처음부터 다시 실행하므로, 자동 시작을 걸면 관제자가 화면을 만질 때마다 로봇에게 "처음부터 다시 돌아라"를 보내게 됩니다. 확인 단계가 있는 버튼으로 했습니다.

지도 파일의 free_thresh 결함 — 미탐사가 자유공간으로 읽히고 있었습니다

순찰 플래너가 factory_map에서 "벽까지 4.61m"를 내놓기에 원본을 열어봤더니, free_thresh: 0.25가 미탐사 픽셀(205)을 자유공간으로 읽고 있었습니다. 점유도가 정확히 0.196이라 0.25 아래로 통과합니다.

의자 다리처럼 "치우면 없어질 물건"이 지도에 박히는 문제

2D LiDAR는 바닥에서 약 0.18m 한 높이만 봅니다. 하필 그 높이에 의자·책상 다리가 걸리고, 매핑 중 서 있던 가구는 지도에 박혀 치워도 남습니다. 그 지도를 Nav2(static layer) · AMCL · patrol_planner가 함께 믿습니다.

SLAM 중에 저절로 안 지워집니다. Cartographer의 서브맵은 num_range_data(기본 90스캔)를 채우면 동결되므로, 나중에 그 자리를 다시 지나가며 빈 공간을 관측해도 옛 서브맵은 바뀌지 않습니다.

새 maps/clean_map.py가 저장된 지도를 후처리합니다. 세 조건을 모두 만족할 때만 지웁니다 — 작다(12셀 이하) · 짧다(0.20m 이하) · 둘레가 전부 자유공간.

LiDAR보다 낮은 장애물에 걸려도 계속 미는 문제

문턱·케이블 트레이·파렛트 하단은 센서로 영영 안 보입니다. 로봇은 앞이 비었다고 믿고 계속 밀어붙이고, 살짝 걸린 정도로는 범퍼도 안 눌립니다.

새 stall_monitor.py가 행동으로 알아냅니다 — "전진 명령이 있는데 지도상 위치가 3초째 그대로다".

/odom이 아니라 TF를 봅니다

바퀴가 헛돌면 오도메트리는 거짓말을 합니다. map → base_footprint TF는 Cartographer 스캔 매칭(이 프로젝트는 use_odometry = false)에서 나오므로 실제로 안 움직였으면 그대로입니다. /odom은 움직였다는데 TF는 그대로면 바퀴 헛돎으로 로그에 구분해 남깁니다.

이 노드가 하지 않는 것

/cmd_vel을 쓰지 않습니다. 순찰 중엔 Nav2가, 매핑 중엔 auto_mapper가 주인이라 여기서 또 쓰면 두 명령이 서로를 밀어냅니다. 알리기만 하고 피하는 건 각자 합니다.

USB 스피커 — 젯슨에서 걸리는 세 가지

함정증상대응
기본 출력이 HDMI 스피커를 꽂아도 무음인데 aplay는 성공(코드 0)으로 끝남 APLAY_DEVICE가 비면 aplay -l을 읽어 USB 카드 자동 선택
카드 번호가 안 고정됨 재부팅·재연결로 plughw:1,0이 다른 장치를 가리킴 번호가 아니라 이름(plughw:CARD=Device,DEV=0)으로 지정
샘플레이트 불일치 piper는 22050Hz, 값싼 USB는 48000Hz만 받음 → hw:로 열면 실패 plughw:로 ALSA가 리샘플링하게 함

첫 번째가 가장 찾기 어렵습니다 — 로그에는 아무 문제가 없는데 소리만 안 납니다. 재생이 실패하면 장치 캐시를 비우고 다음 문장에서 다시 찾으므로, USB를 뽑았다 꽂아 카드 번호가 바뀌어도 복구됩니다.

웹 영상이 느린 원인 — 네 겹

:8500 MJPEG 스트림이 목표 30fps에 못 미치는 원인을 코드에서 찾았습니다. 한 가지가 아니라 네 겹입니다.

① sleep이 인코딩 후에 고정 33ms였습니다

jpeg_bytes = ...encode...   # 20ms 걸렸다 치면
time.sleep(0.033)           # 여기서 또 33ms

실제 주기 = 인코딩 + 33ms = 53ms ≈ 19fps. 주석에는 "약 30 FPS"라 적혀 있는데 실제로는 못 나옵니다.

경과 시간을 빼고 남은 만큼만 자도록 고쳤습니다.

② 클라이언트마다 따로 인코딩했습니다

draw_overlays(2.7MB 복사) + imencode를 연결마다 독립 실행했습니다. 대시보드 iframe + 브라우저 탭 = 정확히 2배. 보는 사람이 늘수록 모두에게 느려집니다.

같은 (프레임, 박스) 조합이면 한 번만 만들어 나눠 쓰는 캐시를 넣었습니다.

③ 카메라 FPS를 요청조차 하지 않았습니다

cap.set(CAP_PROP_FPS, ...)가 없었습니다. 2560×720에서 USB 스테레오 모듈은 흔히 15fps 이하로 협상하고, 그러면 아래를 아무리 고쳐도 그 위로 못 올라갑니다.

요청하고, 거부당하면 시작 로그에 경고합니다. 드라이버 버퍼도 1로 줄였습니다(깊으면 낡은 프레임이 나와 "밀리는" 느낌이 납니다).

④ 08-28 작업이 원인일 수 있습니다

08-28에 넣은 rectification이 캡처 스레드에 있습니다. cv2.remap × 2를 매 프레임 돌리는데, 1280×720 두 장이면 젯슨 CPU에서 프레임당 10~30ms가 나올 수 있고 30fps 예산(33ms)의 절반 이상입니다. 즉 "여전히" 느린 게 아니라 08-28 작업이 더 느리게 만들었을 수 있습니다. 이건 측정해야 알 수 있어 아래 계측을 넣었습니다.

전체 검토에서 찾은 것 — 셸 스크립트 CRLF

셸 스크립트 4개가 CRLF였습니다. 리눅스에서는 이렇게 죽습니다.

bash: ./run_pipeline.sh: /bin/bash^M: bad interpreter: No such file or directory

왜 지금까지 안 드러났나: 저장소(blob)에는 LF로 들어 있고 git 설정이 core.autocrlf=true라 Windows 워킹트리에서만 CRLF가 됩니다. git clone으로 리눅스에 받으면 LF라 문제가 없습니다.

그런데 이 문서는 scp 로 복사하라고 합니다

그러면 Windows 워킹트리의 CRLF가 그대로 젯슨으로 넘어갑니다. 9단계에서 scp -r로 옮기라고 안내한 setup_tts.sh도 한 번 커밋되면 같은 상태가 됩니다.

루트에 .gitattributes를 만들어 *.sh/*.py/ *.lua를 LF로 고정하고, CRLF 4개를 정규화했습니다. 지도(.pgm)·모델(.onnx)은 binary로 명시했습니다.

event_detector에 jetson_principal_x / jetson_principal_y 파라미터를 넣었습니다. 0이면 화면 중심을 써서 예전과 똑같이 동작하므로, 값을 안 넘겨도 지금과 달라지는 것은 없습니다. 젯슨 시작 로그가 넘길 파라미터를 그대로 찍어 주니 복사해 쓰세요(5단계).
